# Boot ROM Support Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the Koh emulator execute a real boot ROM — Koh's own by default, an external dump (stock Nintendo, SGB, AGB) on request — instead of powering on into a cartridge that nothing has initialised.

**Architecture:** `Koh.Emulator.Core` gains a boot ROM *overlay* on the `Mmu` read path plus a one-way `$FF50` unmap latch, loaded through `GameBoySystem.LoadBootRom` **after** construction. The constructor is untouched: `new GameBoySystem` has 67 call sites, most of them tests that drive `Pc`/`Sp` directly and must not have a boot ROM execute, so "won't run without one" is app-layer policy. A new `src/Koh.Boot` project holds `dmg_boot.asm`/`cgb_boot.asm`, assembled at build time by Koh's own `Koh.Asm`/`Koh.Link`.

**Tech Stack:** .NET 10 / C# 14, TUnit for tests, Koh's own RGBDS-dialect assembler, MSBuild for the boot ROM build step.

**Spec:** `docs/superpowers/specs/2026-08-08-boot-rom-design.md` (commit `6ebeb4b`)

## Size risk — read before starting Task 8

A DMG boot ROM is **exactly 256 bytes**. 48 of those are the reference Nintendo logo and 4 are the handoff at `$00FC`, leaving ~204 bytes for: VRAM clear, audio init, logo decompress into VRAM, tilemap write, the scroll animation, the chime, the logo comparison, the header-checksum comparison, and the register handoff. Nintendo fits this in hand-tuned code. An independently written version may not fit on the first attempt.

Mitigation is built into the task order: Task 7 proves the whole build-and-load pipeline with a *minimal* blob, so a size overrun in Task 8 is a contained problem rather than a blocked pipeline. Task 8 Step 1 adds a size assertion that fails loudly. **If the full feature set will not fit, stop and report it — do not silently drop the chime or a validation check.** Both were explicitly chosen by the user and dropping one is a spec change requiring sign-off.

The CGB boot ROM has 2304 bytes and is not size-constrained.

```csharp
namespace Koh.Emulator.Core.Boot;

/// <summary>Which overlay shape a boot ROM has, derived from its length.</summary>
public enum BootRomFamily
{
    /// <summary>256 bytes overlaying $0000-$00FF. DMG, DMG0, MGB, SGB, SGB2.</summary>
    Dmg,

    /// <summary>2304 bytes overlaying $0000-$00FF and $0200-$08FF. CGB, CGB-E, AGB.</summary>
    Cgb,
}

/// <summary>
/// A validated boot ROM image. Construction is the only validation point: past it an
/// invalid blob is unrepresentable, so <see cref="Bus.Mmu"/> never re-checks a size.
///
/// A sealed class rather than a readonly struct on purpose — a struct cannot hold a
/// ReadOnlySpan field, and a struct over a byte[] reintroduces a default(BootRom) with
/// a null array, which is exactly the invalid state this type exists to eliminate.
///
/// Family is derived from LENGTH, not from a caller-declared hardware mode, so an
/// unrecognised but correctly-sized dump (SGB, AGB, a homebrew boot ROM) works with no
/// table of known hashes to keep current.
/// </summary>
public sealed class BootRom
{
    /// <summary>DMG-family boot ROM size: overlays $0000-$00FF.</summary>
    public const int DmgSize = 0x100;

    /// <summary>CGB-family boot ROM size: overlays $0000-$00FF and $0200-$08FF.</summary>
    public const int CgbSize = 0x900;

    private readonly byte[] _bytes;

    private BootRom(byte[] bytes, BootRomFamily family)
    {
        _bytes = bytes;
        Family = family;
        Fingerprint = ComputeFingerprint(bytes);
    }

    public BootRomFamily Family { get; }

    public ReadOnlySpan<byte> Bytes => _bytes;

    /// <summary>
    /// 64-bit FNV-1a over the blob, used by save states to detect that a state was
    /// captured under different boot code. Deliberately not a cryptographic hash: this
    /// guards against confusion, not forgery, and pulling in
    /// System.Security.Cryptography for it would be gratuitous. Never 0 — save states
    /// use 0 to mean "no boot ROM was loaded".
    /// </summary>
    public ulong Fingerprint { get; }

    /// <summary>
    /// Validate and copy a boot ROM image. The copy matters: a caller that reuses its
    /// read buffer must not be able to mutate a blob the machine is already executing.
    /// </summary>
    public static BootRom FromBytes(ReadOnlySpan<byte> bytes)
    {
        var family = bytes.Length switch
        {
            DmgSize => BootRomFamily.Dmg,
            CgbSize => BootRomFamily.Cgb,
            _ => throw new ArgumentException(
                $"Boot ROM is {bytes.Length} bytes. A boot ROM must be either "
                    + $"{DmgSize} bytes (256, DMG family) or {CgbSize} bytes "
                    + $"(2304, CGB family).",
                nameof(bytes)
            ),
        };

        return new BootRom(bytes.ToArray(), family);
    }

    private static ulong ComputeFingerprint(ReadOnlySpan<byte> bytes)
    {
        const ulong offsetBasis = 14695981039346656037UL;
        const ulong prime = 1099511628211UL;

        ulong hash = offsetBasis;
        foreach (byte b in bytes)
        {
            hash ^= b;
            hash *= prime;
        }

        // 0 is the "no boot ROM" sentinel in save states. FNV-1a of an all-zero blob is
        // not 0, but pin the guarantee rather than relying on that.
        return hash == 0 ? 1 : hash;
    }
}
```

```csharp
    /// <summary>
    /// Insert a boot ROM, to execute from $0000 before the cartridge sees control.
    /// Deliberately not a constructor parameter: this type has 67 construction sites,
    /// most of them tests that set Pc/Sp directly and must not have a boot ROM run
    /// first. "Won't run without a boot ROM" is an application-layer policy, not an
    /// invariant of the machine — which is also how SameBoy, mGBA, and ares layer it.
    /// </summary>
    /// <exception cref="ArgumentException">
    /// The blob's family does not match this machine's mode. A CGB machine running a
    /// 256-byte boot ROM is not a device that exists, and accepting it silently
    /// produces behaviour that is very hard to explain later.
    /// </exception>
    /// <exception cref="InvalidOperationException">Execution has already begun.</exception>
    public void LoadBootRom(BootRom rom)
    {
        var expected = Mode == HardwareMode.Cgb ? BootRomFamily.Cgb : BootRomFamily.Dmg;
        if (rom.Family != expected)
            throw new ArgumentException(
```

- [ ] **Step 2: Write the minimal `src/Koh.Boot/dmg_boot.asm`**

Sets the handoff state and unmaps. No animation, no validation yet.

The final two instructions must sit at exactly `$00FC`-`$00FF`: writing `rBANK` drops the overlay, and `PC` then flows straight off the end of the boot ROM into `$0100`. That is how the real hardware hands off, and it is why the boot ROM is exactly 256 bytes.

```
INCLUDE "hardware.inc"

SECTION "BootRom", ROM0[$0000]
Start:
    ld sp, $FFFE          ; stack at the top of HRAM, as hardware leaves it

    ; Clear VRAM $8000-$9FFF. The Mmu $FF-poisons RAM at power-on to catch
    ; read-before-write; a real boot ROM zeroes VRAM, so this is the boot ROM's job
    ; and not the emulator's.
    xor a
    ld hl, $9FFF
.clearVram:
    ld [hl-], a
    bit 7, h              ; still >= $8000?
    jr nz, .clearVram

    ; Audio on, both channels to both outputs, full volume.
    ld a, $80
    ldh [rNR52], a
    ld a, $F3
    ldh [rNR51], a
    ld a, $77
    ldh [rNR50], a

    ; Palettes and LCD on with BG enabled, tile data at $8000.
    ld a, $FC
    ldh [rBGP], a
    ld a, $FF
    ldh [rOBP0], a
    ldh [rOBP1], a
    ld a, $91
    ldh [rLCDC], a

    ; Handoff register state. F cannot be loaded directly, so build AF through the
    ; stack: pushing BC=$00B0 and popping AF leaves F=$B0 (Z set, H set, C set).
    ld bc, $00B0
    push bc
    pop af
    ld bc, $0013
    ld de, $00D8
    ld hl, $014D

    jp Handoff

; The last four bytes of the boot ROM. Writing rBANK unmaps the overlay, and PC then
; runs off the end of the boot ROM straight into the cartridge entry at $0100.
SECTION "Handoff", ROM0[$00FC]
Handoff:
    ld a, $01
    ldh [rBANK], a
```

```csharp
/// <summary>
/// Koh's own boot ROMs, written in Koh assembly under this directory and assembled by
/// Koh's own toolchain at build time.
///
/// These exist because Nintendo's boot ROM cannot be redistributed, and because an
/// emulator that fabricates post-boot state instead of executing boot code is lying
/// about the machine. They are an independent implementation: they owe the observable
/// handoff state, not Nintendo's instruction sequence. One consequence is that DIV at
/// handoff differs, since the cycle counts differ — see the boot ROM spec.
///
/// Users can substitute a real dump at runtime; see Koh.Emulator.App's --boot-rom flags.

    private static byte[] Load(string resourceName)
    {

            Assembly.GetExecutingAssembly().GetManifestResourceStream(resourceName)
            ?? throw new InvalidOperationException(
                $"Embedded boot ROM '{resourceName}' is missing. It is assembled from "
                    + "the .asm sources in src/Koh.Boot by the AssembleBootRoms target; a "
                    + "missing resource means that target did not run or failed silently."
            );

        stream.CopyTo(buffer);

    }
```

- [ ] **Step 3: Implement the full boot ROM**

Rewrite `src/Koh.Boot/dmg_boot.asm`. Structure, in order:

1. `ld sp, $FFFE`; clear VRAM `$8000-$9FFF` (as in Task 6).
2. Audio init: `NR52=$80`, `NR51=$F3`, `NR50=$77`, `NR11=$80`, `NR12=$F3`.
3. **Decompress the cartridge logo into tile data.** Read `$0104-$0133`; for each byte, expand each nibble so every bit becomes two horizontally adjacent pixels, writing two VRAM bytes per nibble with a one-byte gap (the logo is 1bpp doubled). Target `$8010` onward, leaving tile 0 blank.
4. **Write the tilemap row.** Place the logo tiles across a row at `$9904` (row 8, roughly centred).
5. `BGP=$FC`, `OBP0=OBP1=$FF`, `LCDC=$91`.
6. **Validate the logo.** Compare `$0104-$0133` against the 48-byte reference stored in this boot ROM. On mismatch, `jr` to itself — lock up.
7. **Validate the header checksum.** Sum `$0134-$014C` with `checksum = checksum - byte - 1`, compare against `$014D`. On mismatch, lock up.
8. **The scroll.** `SCY` from 100 down to 0, one step per frame, polling `rLY` for `144` to pace it. The logo sits at tilemap y=64, so a large `SCY` puts it above the view and it descends as `SCY` falls.
9. **The chime** at the moment the logo lands: two notes via `NR13`/`NR14` frequency writes with a short gap, then a hold of ~40 frames so the total is ~150.
10. Handoff registers: `AF=$01B0` (build `F` via `push bc` / `pop af`), `BC=$0013`, `DE=$00D8`, `HL=$014D`.
11. `jp Handoff`, with `SECTION "Handoff", ROM0[$00FC]` holding `ld a,$01` / `ldh [rBANK], a`.

The 48-byte reference logo, for step 6 — the same bytes as `Sm83Backend.NintendoLogo` and `samples/gb-2048/src/main.asm:39-41`:

```

    db $CE,$ED,$66,$66,$CC,$0D,$00,$0B,$03,$73,$00,$83,$00,$0C,$00,$0D
    db $00,$08,$11,$1F,$88,$89,$00,$0E,$DC,$CC,$6E,$E6,$DD,$DD,$D9,$99
    db $BB,$BB,$67,$63,$6E,$0E,$EC,$CC,$DD,$DC,$99,$9F,$BB,$B9,$33,$3E
```

Wait for VBlank, used by the scroll loop:

```

    ldh a, [rLY]
    cp 144
    jr nz, .waitVBlank
```

Lock-up on a failed check — deliberately an infinite loop with the LCD left on, so the failure is visible rather than silent:

```

    jr .lockUp
```

2304 bytes, so unlike the DMG one this is not size-constrained. Two `SECTION`s, because `$0100-$01FF` is the cartridge header and not part of the boot ROM image:

```
INCLUDE "hardware.inc"

SECTION "CgbBootLow", ROM0[$0000]
    jp CgbStart

; $0100-$01FF is the cartridge header — a hole in the CGB boot ROM overlay, not part
; of this image. The linker leaves the gap; the Mmu overlay skips it.

SECTION "CgbBootHigh", ROM0[$0200]
CgbStart:
    ...
```

Behaviour, mirroring the DMG one plus the CGB-specific parts:

1. `ld sp, $FFFE`; clear VRAM (both banks — set `rVBK`, clear, restore).
2. Audio init as DMG.
3. Initialise the background palettes through `rBCPS`/`rBCPD` (auto-increment) and the object palettes through `rOCPS`/`rOCPD`.
4. Decompress and place the logo, same algorithm as DMG.
5. Validate the logo and the header checksum. Lock up on failure.
6. Scroll and chime, same shape as DMG.
7. Read the cartridge's CGB flag at `$0143`. If it is not `$80` or `$C0`, this is a DMG cartridge: select a compatibility palette and set `B=$01` for the handoff. Otherwise `B=$00`.
8. Handoff registers: `AF=$1180`, `C=$00`, `DE=$FF56`, `HL=$000D`, `B` per step 7.
9. `SECTION "CgbHandoff", ROM0[$08FC]` with `ld a,$01` / `ldh [rBANK], a` — the same trick as DMG, at the end of the 2304-byte image so `PC` flows to... **note:** on CGB the image ends at `$08FF`, so `PC` would flow into `$0900`, not `$0100`. The CGB boot ROM must therefore `jp $0100` explicitly after unmapping. Place `ld a,$01` / `ldh [rBANK],a` / `jp $0100` at the end of the code; the exact address does not matter as it does on DMG.

Selection policy lives in the app, not in Core. Per-family slots exist because the mode is resolved per cartridge, so a single path is not enough for a session that opens both a DMG and a CGB game.

```csharp
using Koh.Emulator.Core;
using Koh.Emulator.Core.Boot;

namespace Koh.Emulator.App;

/// <summary>
/// Chooses which boot ROM to insert. This is application policy, not machine
/// behaviour: Koh.Emulator.Core takes bytes and does not care where they came from.
///
/// Koh's own boot ROMs are the default so the emulator works out of the box; a user
/// who owns a real dump can substitute it. Nintendo's boot ROM is never bundled,
/// downloaded, or cached.
/// </summary>
public sealed class BootRomResolver(string? anyPath, string? dmgPath, string? cgbPath)
{
    public BootRom Resolve(HardwareMode mode)
    {
        // --boot-rom applies to whichever family the loaded cartridge resolved to.
        string? path =
            anyPath ?? (mode == HardwareMode.Cgb ? cgbPath : dmgPath);

        if (path is null)
            return BootRom.FromBytes(
                mode == HardwareMode.Cgb ? KohBootRoms.Cgb : KohBootRoms.Dmg
            );

        if (!File.Exists(path))
            throw new FileNotFoundException(
                $"Boot ROM '{path}' not found. Omit the flag to use Koh's own boot ROM.",
                path
```
